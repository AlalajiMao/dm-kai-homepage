Implement Queue using Stacks
Easy Stack Stack Simulation Design
Problem Statement

Implement a first-in first-out (FIFO) queue using only two stacks. The implemented queue should support all the functions of a normal queue.

  • MyQueue() — initialises the queue.
  • void push(int x) — pushes element x to the back of the queue.
  • int pop() — removes and returns the element from the front.
  • int peek() — returns the element at the front without removing it.
  • boolean empty() — returns true if the queue is empty.

You must use only standard stack operations: push to top, peek/pop from top, size, and empty.

EXAMPLE
push(1), push(2)
peek() → 1
pop() → 1
empty() → false

Here's a classic design problem. I want you to build a queue — FIFO semantics — using only stacks as your underlying data structure. You can use two stacks. The queue needs push, pop, peek, and empty. The operations you're allowed on a stack are push-to-top, pop-from-top, peek-top, size, and empty check. What are your initial thoughts?
Me
Candidate
The core tension here is that a stack is LIFO — last in, first out — while a queue is FIFO. A single stack reverses the order. But if you pour one stack into another, you reverse it again, which restores the original order. That's the key. Let me think about how to structure that cleverly with two stacks before asking my clarifying questions.
Stage 2 — Clarifying Questions

  • Can pop() and peek() be called on an empty queue, or can I assume the queue is non-empty?
  • Is there any constraint on time complexity you're targeting — strictly O(1) per operation, or is amortised O(1) acceptable?

Interviewer

Stage 3 — Approach Discussion
Me
Candidate
Let me compare two approaches.

Eager approach (brute force style): On every push, move everything from stack2 to stack1, push the new element, then move it all back. This gives O(n) per push but O(1) pop and peek. It works, but it's wasteful.

Lazy transfer approach: Designate stack1 as the inbox (new elements always push here) and stack2 as the outbox (pop and peek from here). When you need to pop or peek and the outbox is empty, pour the entire inbox into the outbox — this reverses the order, putting the oldest element on top. Crucially, you only do this transfer when the outbox runs dry.

Each element crosses from inbox to outbox at most once in its lifetime, so the total transfer cost across all operations is O(n) for n elements. That gives amortised O(1) per operation. I'll go with the lazy approach.
The key invariant: the outbox is only ever replenished all at once, and only when empty. This means we never mix "generations" — everything in the outbox arrived before everything in the inbox. FIFO order is preserved automatically.
IV
Interviewer
Good reasoning. Can you convince me the amortised argument is actually correct? Isn't it possible that every single pop() triggers a full transfer?
Me
Candidate
That's a fair challenge. A transfer only happens when the outbox is empty. After a transfer, the outbox has k elements in it. Those k elements each get popped one by one — k separate pop() calls, each O(1), before the outbox is empty again. So the cost of that one transfer (O(k)) is spread over k future pops — O(1) amortised per pop. The worst-case for any single pop is O(n), but you can only hit that worst case once every n pops.
Stage 4 — Code Walkthrough
Me
Candidate
Let me write it out. I'll pull the transfer logic into a helper to keep things clean.
Python 3 — Queue using Stacks (walkthrough)
class MyQueue:
    def __init__(self):
        self.inbox  = []  # stack 1: new elements pushed here
        self.outbox = []  # stack 2: dequeue from here (FIFO order)

    def _transfer(self) -> None:
        # Only move when outbox is completely empty.
        # Popping inbox and pushing to outbox reverses the order.
        if not self.outbox:
            while self.inbox:
                self.outbox.append(self.inbox.pop())

    def push(self, x: int) -> None:
        self.inbox.append(x)  # always push to inbox — O(1)

    def pop(self) -> int:
        self._transfer()          # ensure outbox has elements
        return self.outbox.pop()  # front of queue is top of outbox

    def peek(self) -> int:
        self._transfer()
        return self.outbox[-1]   # peek without removing

    def empty(self) -> bool:
        return not self.inbox and not self.outbox
Me
Candidate
Let me trace the example: push(1), push(2), push(3)

After pushes: inbox=[1,2,3], outbox=[]

pop() — outbox is empty, transfer: pop inbox one by one → outbox=[3,2,1]. Now pop outbox → returns 1. outbox=[3,2].

peek() — outbox is not empty, no transfer needed. outbox[-1] = 2. ✓

push(4) — inbox=[4], outbox=[3,2]. Both stacks live side by side, no conflict.

pop() — outbox not empty, pop → returns 2. ✓ (FIFO preserved)
IV
Interviewer
Good. What happens to empty() if there are elements in inbox but outbox is empty?
Me
Candidate
That's exactly why I check both stacks in empty(): not self.inbox and not self.outbox. If inbox has elements and outbox is empty, the queue is not empty. A common bug is checking only one of the two — that would give a wrong answer in exactly that scenario.

Stage 6 — Follow-up Questions
IV
Interviewer
A few follow-ups: (1) Can you implement a queue with only one stack? (2) How would you go the other direction — implement a stack using queues? (3) Does your solution handle interleaved pushes and pops correctly?
Me
Candidate
(1) Queue with one stack: You can use the call stack — recursion. To dequeue, recurse down to the bottom of the stack, remove it, and return. But that's O(n) per dequeue and uses O(n) call stack space. Not practical — but it technically works with one explicit stack.

(2) Stack using queues: The reverse problem. Use one queue. On each push, enqueue the new element, then rotate the queue (dequeue everything and re-enqueue it) so the new element lands at the front. This makes push O(n) but pop O(1). Or do the rotation lazily on pop instead — same trade-off, different direction.

(3) Interleaved operations: Yes, absolutely. The key is that the outbox is never partially filled — we only add to it when it's completely empty. So any elements already in the outbox (pushed before the last transfer) are always older than everything in the inbox. FIFO order is guaranteed at all times.

✅ Full Python Solution

Python 3 — Implement Queue using Stacks O(1) amortised · O(n) space 
class MyQueue:
    def __init__(self):
        self.inbox  = []
        self.outbox = []

    def _transfer(self) -> None:
        if not self.outbox:
            while self.inbox:
                self.outbox.append(self.inbox.pop())

    def push(self, x: int) -> None:
        self.inbox.append(x)

    def pop(self) -> int:
        self._transfer()
        return self.outbox.pop()

    def peek(self) -> int:
        self._transfer()
        return self.outbox[-1]

    def empty(self) -> bool:
        return not self.inbox and not self.outbox
Key Interview Tips 面试要点
  • Transfer lazily — only when the outbox is empty, never on every push
  • Each element moves from inbox to outbox at most once — that's the amortised O(1) argument
  • In empty(), check both stacks — a common bug is checking only one
  • Explain the amortised analysis clearly: worst-case single pop is O(n), but you can only hit that once every n pops
  • The two-stack trick works because reversing twice restores FIFO order
