LRU Cache
Hard HashMap + Doubly-Linked List Linked List
Problem Statement

Design a data structure that follows the constraints of a Least Recently Used (LRU) cache.

Implement the LRUCache class with:

  • LRUCache(int capacity) — initialize with positive capacity.
  • int get(int key) — return the value if key exists, else -1. Mark as recently used.
  • void put(int key, int value) — insert or update key. If capacity is exceeded, evict the least recently used key.

Both get and put must run in O(1) average time complexity.

EXAMPLE
LRUCache(2)
put(1,1) → cache: {1:1}
put(2,2) → cache: {1:1, 2:2}
get(1) → 1      (key 1 is now MRU)
put(3,3) → evicts key 2 (LRU). cache: {1:1, 3:3}
get(2) → -1     (was evicted)
get(3) → 3

After get(1), the recency order is [2(LRU), 1(MRU)]. When put(3,3) comes in, key 2 is the LRU and gets evicted.

💬 Mock Interview

The LRU Cache is a classic system design meets data structures question. The O(1) constraint on both operations forces a specific combination: a hash map for O(1) key lookup, and a doubly-linked list for O(1) promotion to "most recently used" and O(1) eviction of the "least recently used." Sentinel head/tail nodes eliminate all edge cases in the pointer manipulation.

Stage 1 — Problem Introduction
IV
Interviewer
Design an LRU cache with a fixed capacity. It supports get and put, both in O(1) time. When the cache is full and a new key is inserted, the least recently used key is evicted. Both get and put count as a "use." How would you implement this?
Me
Candidate
The key challenge is two O(1) operations at once: look up a key by value, and track usage order so I can find and evict the LRU item. A hash map alone handles lookup but not ordering. A linked list alone tracks order but not lookup. Combining them gives me both: hash map for O(1) key-to-node lookup, doubly-linked list for O(1) insertion, deletion, and order maintenance.
Stage 2 — Clarifying Questions
Me
Candidate
A few quick clarifications:
  • If I call put on an existing key, does it update the value and move it to MRU? (I'll assume yes.)
  • What if capacity is 1? My solution should handle that edge case naturally.
  • Are keys and values always integers?
  • Is thread safety a concern here, or just single-threaded correctness?
IV
Interviewer
Yes — put on an existing key updates the value and marks it as most recently used. Keys and values are integers. Single-threaded for now, though feel free to mention thread safety as a follow-up.
Stage 3 — Approach Discussion
Me
Candidate
The classic O(1) design uses two data structures together:

Hash map: key → node — gives O(1) access to any node by key.
Doubly-linked list (DLL): nodes ordered by recency — head side is LRU, tail side is MRU. The DLL must be doubly-linked because deleting an arbitrary node requires updating both its predecessor and successor, and with only a singly-linked list we'd need O(n) to find the predecessor.

Two sentinel nodes (dummy head and dummy tail) make pointer operations uniform: we never have to check "is this the first/last real node?" — the sentinels absorb those edge cases.

get(key): look up in map, move node to just before tail (MRU position), return value.
put(key, value): if key exists, update and move to MRU. If not, create new node at MRU position. If over capacity, remove the node just after head (LRU position) and delete from map.
The sentinel head represents "before everything" (LRU side) and the sentinel tail represents "after everything" (MRU side). Adding to MRU = inserting between tail.prev and tail. Removing LRU = removing head.next. Every get and put becomes: remove node from its current position + insert at MRU. The two helpers _remove and _add_to_front do exactly that. Keeping them as separate methods makes the code easier to reason about and test.
Me
Candidate
I'll implement a DLinkedNode class and an LRUCache class. Two private helpers: _remove(node) and _add_to_front(node).
IV
Interviewer
Walk me through the pseudocode and trace the example: capacity=2, put(1,1), put(2,2), get(1), put(3,3), get(2).
Stage 4 — Pseudocode & Trace
Me
Candidate
Here's the pseudocode for the key operations:
Pseudocode
# DLL layout: head(LRU sentinel) ↔ ... nodes ... ↔ tail(MRU sentinel)
# head.next = LRU node;  tail.prev = MRU node

function _remove(node):
    node.prev.next = node.next
    node.next.prev = node.prev

function _add_to_front(node):      # insert between head and head.next
    node.next      = head.next
    node.prev      = head
    head.next.prev = node
    head.next      = node

function get(key):
    if key not in cache: return -1
    node = cache[key]
    _remove(node)
    _add_to_front(node)
    return node.val

function put(key, value):
    if key in cache:
        _remove(cache[key])
    node = DLinkedNode(key, value)
    _add_to_front(node)
    cache[key] = node
    if len(cache) > cap:
        lru = tail.prev           # LRU is at tail end (MRU sentinel's prev)
        _remove(lru)
        del cache[lru.key]
Me
Candidate
Wait — let me correct the sentinel orientation. I'll use head as the LRU sentinel and tail as the MRU sentinel. The MRU node is adjacent to the head (head.next = MRU), and the LRU node is adjacent to the tail (tail.prev = LRU). So _add_to_front inserts between head and head.next (the MRU end), and eviction removes tail.prev (the LRU end).

Let me trace: capacity=2.

put(1,1): create node(1,1), insert at MRU. DLL: H ↔ [1] ↔ T. cache={1:node1}
put(2,2): create node(2,2), insert at MRU. DLL: H ↔ [2] ↔ [1] ↔ T. cache={1,2}. Not over capacity.
Recency: MRU=2, LRU=1

get(1): found. Remove node1 from middle, re-insert at MRU.
DLL: H ↔ [1] ↔ [2] ↔ T. Recency: MRU=1, LRU=2 Return 1.

put(3,3): key 3 not in cache. Create node(3,3), insert at MRU.
DLL: H ↔ [3] ↔ [1] ↔ [2] ↔ T. len=3 > cap=2.
Evict tail.prev = node2. Remove it. del cache[2].
DLL: H ↔ [3] ↔ [1] ↔ T. cache={1,3}

get(2): key 2 not in cache → return -1 ✅
get(3): found → return 3 ✅
IV
Interviewer
Good trace. Why do you need a doubly-linked list specifically — would a singly-linked list work?
Me
Candidate
No. To delete an arbitrary node in O(1), I need to update both its predecessor's next and its successor's prev. With a singly-linked list, given only the node itself, I can't access its predecessor without scanning from the head — O(n). The doubly-linked list gives me node.prev directly, making deletion O(1).
Stage 5 — Complexity Analysis
Me
Candidate

Time — put: O(1) — same operations plus optionally one eviction (remove + map delete), all O(1).

Space: O(capacity) — the hash map and DLL together store at most capacity nodes plus 2 sentinel nodes.

Stage 6 — Follow-up Questions
IV
Interviewer
What if get and put are called concurrently from multiple threads?
Me
Candidate
This implementation is not thread-safe. Concurrent writes could corrupt the DLL pointer state or the hash map. To make it thread-safe I'd wrap get and put with a mutex lock — in Python, threading.Lock() around the method body. Alternatively, use a read-write lock to allow concurrent reads when no write is happening. For high-throughput scenarios, lock striping by key hash is another option. But that's system design territory — in a coding interview I'd call out the issue and propose the simple mutex approach.
IV
Interviewer
How would you implement an LFU (Least Frequently Used) cache instead?
Me
Candidate
LFU is significantly harder — that's LC #460. The idea: maintain a hash map of frequency buckets, where each bucket is itself an ordered collection of keys at that frequency. Also maintain a min_freq counter. On access, move the key from its current bucket to the next higher bucket. On eviction, remove the LRU item from the min_freq bucket. Each bucket can be implemented as a doubly-linked list for O(1) ordering, with another hash map for key-to-node access within each bucket. The overall data structure is more complex but still achieves O(1) amortized per operation.
IV
Interviewer
Why did you choose to store the key inside the DLL node rather than just the value?
Me
Candidate
Eviction. When I remove the LRU node from the DLL tail, I need to also delete it from the hash map — which requires the key. If the node only stores its value, I'd have to search the hash map to find which key maps to this node — O(n). Storing the key in the node makes eviction O(1): del cache[lru.key].

✅ Full Python Solution

Python 3 — LRU Cache O(1) get/put · O(capacity) space 
class DLinkedNode:
    def __init__(self, key=0, val=0):
        self.key  = key
        self.val  = val
        self.prev = self.next = None


class LRUCache:
    def __init__(self, capacity: int):
        self.cap   = capacity
        self.cache = {}            # key -> DLinkedNode
        # sentinel head (LRU side) and tail (MRU side)
        self.head  = DLinkedNode()
        self.tail  = DLinkedNode()
        self.head.next = self.tail
        self.tail.prev = self.head

    def _remove(self, node: DLinkedNode) -> None:
        node.prev.next = node.next
        node.next.prev = node.prev

    def _add_to_front(self, node: DLinkedNode) -> None:
        # Insert between head and head.next (MRU position)
        node.next      = self.head.next
        node.prev      = self.head
        self.head.next.prev = node
        self.head.next      = node

    def get(self, key: int) -> int:
        if key not in self.cache:
            return -1
        node = self.cache[key]
        self._remove(node)
        self._add_to_front(node)
        return node.val

    def put(self, key: int, value: int) -> None:
        if key in self.cache:
            self._remove(self.cache[key])
        node = DLinkedNode(key, value)
        self._add_to_front(node)
        self.cache[key] = node
        if len(self.cache) > self.cap:
            lru = self.tail.prev        # LRU node is adjacent to tail sentinel
            self._remove(lru)
            del self.cache[lru.key]
Key Interview Tips 💡
  • State the two-structure insight upfront: hash map for O(1) lookup, doubly-linked list for O(1) ordering and eviction.
  • Use sentinel head and tail nodes — they eliminate all "is this the first/last node?" edge cases and make _remove and _add_to_front uniform.
  • Store the key inside each DLL node — eviction requires deleting from the hash map, which needs the key. This is the most common detail candidates forget.
  • Extract _remove and _add_to_front as private helpers — both get and put call them, so the helpers eliminate repetition and make the logic auditable.
  • In Python, OrderedDict implements exactly this pattern internally and can be used for a one-liner LRU. Mention it as trivia but implement the DLL version to demonstrate understanding.
  • The key interview concept: whenever you need O(1) ordered eviction, think HashMap + Doubly-Linked List. This pattern extends to LFU (LC #460) with buckets per frequency.
