Merge k Sorted Lists
Hard Merge + Heap Linked List
Problem Statement

You are given an array of k linked-lists lists, each linked-list is sorted in ascending order.

Merge all the linked-lists into one sorted linked-list and return it.

EXAMPLE
Input: lists = [1→4→5, 1→3→4, 2→6]
Output: 1→1→2→3→4→4→5→6

At each step, pick the minimum head across all k lists. A min-heap keeps that minimum retrieval at O(log k) rather than O(k).

💬 Mock Interview

This is the generalization of #21 (merge two lists) to k lists. The brute-force approach scans all k heads on every step — O(nk) total. The optimal approach uses a min-heap to find the minimum head in O(log k), dropping the total to O(n log k). Python's heapq needs a tiebreaker to avoid comparing ListNode objects directly.

Stage 1 — Problem Introduction
IV
Interviewer
You have k sorted linked lists. Merge them all into a single sorted linked list and return it. For example, with lists [1→4→5, 1→3→4, 2→6] the answer is 1→1→2→3→4→4→5→6. What's your initial thinking?
Me
Candidate
This is merge-two-lists extended to k lists. The key operation is always: pick the smallest current head across all k lists. If I scan all k heads each time, that's O(k) per node — O(nk) total. I want to speed up the "find the minimum" step, which is exactly what a min-heap does: O(log k) per extraction.
Stage 2 — Clarifying Questions
Me
Candidate
A few quick questions:
  • Can any of the k lists be empty or null? I'll skip those when initializing the heap.
  • Can k itself be zero (empty array of lists)?
  • Are node values integers? I need that to define heap order.
  • Are there duplicate values across lists? (The example has two 1s and two 4s, so yes — that's fine.)
IV
Interviewer
Yes, individual lists can be null — skip them. k can be zero — return null. Values are integers. Duplicates are allowed.
Stage 3 — Approach Discussion
Me
Candidate
Three approaches in order of sophistication:

Brute force — collect and sort: Walk all lists, collect every value, sort, rebuild. O(n log n) time, O(n) space. Simple but ignores the sorted structure.

Sequential merge: Merge list 1 with list 2, then merge result with list 3, etc. Each merge is O(n·i) work in the worst case — total is O(nk). Better but still not optimal.

Min-heap: Push the head of each list into a heap keyed by value. Repeatedly pop the minimum, append it to the result, and push its next node. O(n log k) time, O(k) space for the heap.

Divide and conquer: Pair up lists, merge pairs, repeat. Same O(n log k) complexity as heap. Possibly better cache behavior but more code.

I'll go with the heap — it's concise and directly reflects the intuition.
Python's heapq compares tuple elements left to right. If two nodes have the same value, comparing ListNode objects would raise a TypeError. Fix: use (node.val, index, node) where index is the list's position in the input array. Index breaks ties deterministically without ever needing to compare nodes.
IV
Interviewer
Good. Walk me through the heap approach with pseudocode and a trace on the example.
Stage 4 — Pseudocode & Trace
Me
Candidate
Here's the pseudocode:
Pseudocode
function mergeKLists(lists):
    heap = []

    # Seed heap with first node of each non-empty list
    for i, node in enumerate(lists):
        if node:
            heappush(heap, (node.val, i, node))

    dummy = cur = ListNode(0)

    while heap:
        val, i, node = heappop(heap)   # pop minimum
        cur.next = node                  # append to result
        cur = cur.next
        if node.next:
            heappush(heap, (node.next.val, i, node.next))

    return dummy.next
Me
Candidate
Tracing [1→4→5, 1→3→4, 2→6] — I'll label lists L0, L1, L2.

Seed heap: push (1,0,L0[1]), (1,1,L1[1]), (2,2,L2[2])
Heap: [(1,0,1), (1,1,1), (2,2,2)]

Pop (1,0,1): append 1. Push L0's next: (4,0,4). Result: 1
Pop (1,1,1): append 1. Push L1's next: (3,1,3). Result: 1→1
Pop (2,2,2): append 2. Push L2's next: (6,2,6). Result: 1→1→2
Pop (3,1,3): append 3. Push (4,1,4). Result: 1→1→2→3
Pop (4,0,4): append 4. Push (5,0,5). Result: 1→1→2→3→4
Pop (4,1,4): append 4. No next — nothing pushed. Result: 1→1→2→3→4→4
Pop (5,0,5): append 5. No next. Result: 1→1→2→3→4→4→5
Pop (6,2,6): append 6. No next. Result: 1→1→2→3→4→4→5→6 ✅
IV
Interviewer
Perfect trace. Why do you need the index i in the heap tuple?
Me
Candidate
Python's heapq compares tuples element by element. If two nodes have equal values, it falls through to compare the next element in the tuple. Without the index, it would try to compare two ListNode objects directly — which raises a TypeError because ListNode doesn't define __lt__. The index i is always unique per list, so it breaks ties before Python ever touches the node object.
Stage 5 — Complexity Analysis
Me
Candidate
Time: O(n log k) — there are n total nodes across all lists. Each node is pushed once and popped once. Each heap operation is O(log k) because the heap holds at most k elements at any time.

Space: O(k) — the heap holds at most one node per list. The output list is O(n) but that's required output, not auxiliary.

Stage 6 — Follow-up Questions
IV
Interviewer
Why is the heap approach O(n log k) and not O(nk)?
Me
Candidate
Without a heap, finding the minimum across k list heads requires scanning all k of them — O(k) work per node. Across n nodes that's O(nk). The heap always contains exactly at most k elements — one per list — so each push and pop is O(log k), not O(k). Total: O(n log k). For large k, log k grows much slower than k — for k=1000, log k ≈ 10.
IV
Interviewer
How does divide and conquer compare to the heap approach?
Me
Candidate
Both are O(n log k) time. Divide and conquer merges pairs of lists — in log k rounds, each round touching all n nodes total. The heap processes one node at a time with O(log k) overhead each. In practice, divide and conquer may have better cache locality since it works on contiguous list segments. The heap is usually simpler to write correctly in an interview. For Python specifically, the heap avoids recursion depth issues that D&C might encounter on very large inputs.
IV
Interviewer
What if k is 1? What if k is very large — say, 10,000?
Me
Candidate
k=1: the heap has at most one element at a time — it degenerates to a linear scan, O(n log 1) = O(n). Correct. k=10,000: the heap-based approach is fine — heap size is 10,000, log(10,000) ≈ 13, so each operation is still cheap. Memory for the heap is O(k) = 10,000 nodes which is trivial. The algorithm scales well.

✅ Full Python Solution

Python 3 — Merge k Sorted Lists O(n log k) time · O(k) space 
import heapq

class Solution:
    def mergeKLists(self, lists: List[Optional[ListNode]]) -> Optional[ListNode]:
        heap = []
        for i, node in enumerate(lists):
            if node:
                heapq.heappush(heap, (node.val, i, node))

        dummy = cur = ListNode(0)
        while heap:
            val, i, node = heapq.heappop(heap)
            cur.next = node
            cur = cur.next
            if node.next:
                heapq.heappush(heap, (node.next.val, i, node.next))

        return dummy.next
Key Interview Tips 💡
  • Always use a dummy head to simplify result list construction — avoids special-casing the very first node.
  • In Python, heap tuple must be (val, index, node) — the index prevents a TypeError when two nodes share the same value and Python tries to compare ListNode objects.
  • Seed the heap with the first node of each non-empty list only — skip null entries upfront.
  • State the complexity clearly: "n total nodes, k-element heap, so O(n log k) time and O(k) space."
  • Mention divide-and-conquer as an equally valid O(n log k) alternative — same complexity, different constant factors.
  • This problem is a direct extension of #21 (merge two lists) — frame it that way to show pattern recognition.
