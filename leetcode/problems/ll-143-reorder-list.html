Reorder List
Medium Fast & Slow + Reversal + Merge Linked List
Problem Statement

Given the head of a singly linked list L0 → L1 → … → Ln, reorder it in-place to: L0 → Ln → L1 → Ln-1 → L2 → Ln-2 → …

You may not alter the values in the list's nodes. Only nodes themselves may be changed. Modify the list in-place — do not return anything.

EXAMPLES
Input: 1 → 2 → 3 → 4
Output: 1 → 4 → 2 → 3

Input: 1 → 2 → 3 → 4 → 5
Output: 1 → 5 → 2 → 4 → 3

The pattern zippers the front half with the reversed back half. The middle node (for odd-length lists) ends up as the final node.

💬 Mock Interview

Reorder List is a synthesis problem — it combines three fundamental linked-list techniques back-to-back: fast/slow pointer to find the middle, in-place reversal of the second half, and alternating merge of two lists. Recognizing this decomposition is the key insight.

Stage 3 — Approach Discussion
Me
Candidate
Let me compare two approaches:

Array/deque approach: Collect all nodes into a list or deque, then use two pointers (front and back) to weave them back into a chain. Works in O(n) time and O(n) space. Simple to implement but wastes space — you're storing references to all nodes.

Three-step in-place:
  1. Find the middle using fast/slow pointers. Slow ends up at the midpoint.
  2. Reverse the second half in-place using the standard three-pointer reversal — starting from slow.next, and severing slow.next = None to cut the list in two.
  3. Merge the two halves by alternating: take one node from the front list, then one from the back (reversed) list, repeat until the back list is exhausted.
This is O(n) time and O(1) space — no auxiliary storage.

I'll go with the three-step approach since it demonstrates the in-place linked-list techniques directly.
The merge step is subtler than it looks. I need to save first.next and second.next before relinking, because I'm about to overwrite both. Also, the second list is always one node shorter than or equal to the first (the middle node stays in the first half), so I loop "while second" — when second is exhausted, the first list tail is correctly in place already.

Stage 4 — Pseudocode & Trace
Me
Candidate
Here's the three-step pseudocode:
Pseudocode — Find Middle · Reverse · Merge
function reorderList(head):
    # ── Step 1: Find middle via fast/slow pointers ──────────
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
    # slow is now at the middle node

    # ── Step 2: Reverse the second half ─────────────────────
    prev, cur = None, slow.next
    slow.next = None          # sever the list at the middle
    while cur:
        nxt      = cur.next
        cur.next = prev
        prev     = cur
        cur      = nxt
    # prev is now the head of the reversed second half

    # ── Step 3: Merge two halves by interleaving ────────────
    first, second = head, prev
    while second:
        tmp1         = first.next
        tmp2         = second.next
        first.next   = second   # weave second after first
        second.next  = tmp1    # weave tmp1 after second
        first        = tmp1    # advance first
        second       = tmp2    # advance second

Space: O(1) — only a constant number of pointer variables are used across all three steps. The reversal and merge both work entirely in-place with no auxiliary allocation.

Stage 6 — Follow-up Questions
IV
Interviewer
Why do you split at the middle specifically? Could you split at any other point?
Me
Candidate
The problem requires interleaving from the front and the back simultaneously, consuming equal numbers of nodes from each end. The middle split ensures the two halves are as equal as possible — length n/2 each (or one node longer for the first half when n is odd). If you split anywhere else, one half would run out before the other and you'd get malformed output. The middle is the unique split point that makes the interleaving well-defined for any list length.
IV
Interviewer
How is this problem different from LC #92 (Reverse Linked List II)?
Me
Candidate
LC #92 reverses a contiguous subrange of a list and leaves the surrounding nodes in place — the result is still one straight chain, just with a segment flipped. LC #143 (this problem) reverses the second half and then interleaves it with the first half, weaving two separate chains into one. The reversal step uses the same mechanics as #92, but the merge step is entirely new — it's an alternating splice rather than a simple pointer reattachment.
IV
Interviewer
Why loop on while second in the merge step, rather than while first?
Me
Candidate
The second half is always less than or equal to the length of the first half — for odd-length lists, the first half has one extra node (the middle), and for even-length lists they're equal. By looping on while second, once the second half is exhausted, the first half's tail is already in its correct final position (it naturally has no more nodes to interleave after), so we can stop. If I looped on while first for an odd-length list, I'd dereference second when it's None on the last iteration and crash.

✅ Full Python Solution

Python 3 — Reorder List O(n) time · O(1) space 
class Solution:
    def reorderList(self, head: Optional[ListNode]) -> None:
        # ── Step 1: Find middle via fast/slow pointers ──────────
        slow = fast = head
        while fast and fast.next:
            slow = slow.next
            fast = fast.next.next

        # ── Step 2: Reverse the second half ─────────────────────
        prev, cur = None, slow.next
        slow.next = None          # sever the list at the midpoint
        while cur:
            nxt      = cur.next
            cur.next = prev
            prev     = cur
            cur      = nxt

        # ── Step 3: Merge two halves by interleaving ────────────
        first, second = head, prev
        while second:
            tmp1, tmp2 = first.next, second.next
            first.next  = second    # splice second after first
            second.next = tmp1     # splice tmp1 after second
            first       = tmp1     # advance to next first-half node
            second      = tmp2     # advance to next second-half node
Key Interview Tips 💡
  • State the decomposition upfront: find middle → reverse second half → interleave merge. Interviewers reward clear structure.
  • Always slow.next = None after finding the middle — if you forget to sever, the reversed half still points into the original chain and you get an infinite loop during the merge.
  • In the merge step, save both tmp1 = first.next and tmp2 = second.next before relinking anything — you need both to advance the pointers afterward.
  • Loop on while second, not while first. Second is always ≤ length of first; the first-half tail self-terminates when second is exhausted.
  • The fast/slow pointer stops when fast or fast.next is None — for even-length lists, fast lands on the last node; for odd, fast falls off the end. Either way, slow = correct middle.
  • This problem is a combination of #876 (find middle), #206 (reverse), and the merge logic from #21 — mention that to show you see the building blocks.
